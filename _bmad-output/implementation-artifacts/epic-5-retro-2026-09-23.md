### Cross-story defects (lens reviews)

**F1. The debug trigger shows "recording" after the stage ends the capture itself (high, fix now).** `DebugCaptureTrigger.toggle()` is the only writer of `isRecording` and `liveMeetingID` (`Sources/AppUI/DebugCaptureTrigger.swift:47-65`). `CaptureStage.fail()` ends a capture on mic revocation, the transient cap, or `all_sources_lost`, and clears `live[meetingID]` (`Sources/Capture/CaptureStage.swift:398-419`). The trigger never learns of it. The toolbar indicator and the menu title then claim a recording that is not happening. The next Cmd-Shift-R press only clears the stale state. No test emits a fault through the trigger (`Tests/AppUITests/DebugCaptureTriggerTests.swift`). All three lenses found this. Commits `4ac060e` against `19131e7`. This defect sits on the exact path the Story 5.6 live run exists to exercise.

**F2. Write failures during capture never reach persisted state (high, fix now).** `CaptureStage.stop` copies only `exactZeroSeconds` and `rebuildCount` from `watchdogStats` into `CaptureMeta` (`CaptureStage.swift:291-297`). `firstWriteErrorDescription` (`Sources/Capture/CaptureWatchdog.swift:22`) and the ring drop counts have no reader. A disk-full event mid-capture lands the row in `captured`, and the pipeline runs on truncated audio. Commit `86f9b8c` calls this field "the sole signal" for write errors. Related: a failed flush or finalize in `stop()` leaves the WAV header unpatched on a `capture_failed` row, and launch recovery never repairs it (`CaptureSession.swift:313-327`).

**F3. Captured meetings can strand with no recovery owner (medium, fix now).** If `recordCaptureFinished` throws after the WAV is final, the row stays `recording`, and launch recovery later relabels it `recovered_after_interruption` (`CaptureStage.swift:298-308`). `onCaptured` runs in an unstructured `Task`. If `Config.load()` fails, or the app quits mid-pipeline, the meeting stays in `captured` or `transcribing`. The app never runs `Orchestrator.CrashRecovery`, and no path re-drives `captured` rows (`App/Auricle/AuricleApp.swift:41-46`, `:171-194`).

**F4. First-run flow has two dead ends (medium, fix now).** `OnboardingMarker.exists` is a plain read inside `body` (`AuricleApp.swift:50`). After Done writes the marker, the window stays on "You're set up" until relaunch, and `notificationDelegate` stays built from the pre-onboarding config. The Debug command is attached whether or not onboarding is complete (`AuricleApp.swift:60-71`). Cmd-Shift-R during onboarding starts a real capture with no indicator and no mic-denied alert.

**F5. Capture-to-pipeline wiring lives only in `App/` (medium, fix now).** `runPipelineAfterCapture` hard-codes `RunOptions(to: .reviewDiarization)` and silently returns on an unreadable config (`AuricleApp.swift:171-194`). `vaultPathValidationError(from:)` maps error types in `App/` too (`:121-130`). `swift test` reaches neither. The production revocation classifier `LiveCaptureSession.engineConfigurationChanged()` also has no test that can reach it (`Sources/Capture/LiveCaptureSession.swift:137-150`). The existing tests use a denied-mic checker, so the observer never fires.

**F6. Capture robustness items that the live run should settle (defer to after the live run).**
- Three mic transients in 30s fail the whole capture, while system-audio loss only degrades it (`CaptureStage.swift:349-357`). A mic that fails to start also fails the capture (`CaptureSession.swift:209-216`).
- Each `AVAudioEngineConfigurationChange` yields one fault, with no coalescing (`LiveCaptureSession.swift:137-149`). The 5.4 spec deferred this to the 5.6 live run, and 5.6 scoped the live run out.
- Mic buffers with more than 2 channels are dropped and never counted (`AudioRingBuffer.swift:139`). The tap reads only `mBuffers[0]`, which can be a headset input stream (`ProcessTapSource.swift:264-265`).
- `restart` can race `stop` (`LiveCaptureSession.swift:114-131`). `ProcessTapSource.deinit` can run `queue.sync` on its own queue (`ProcessTapSource.swift:76-82`, `RebuildCoordinator.swift:60-64`).
- A second system-audio loss keeps the first loss's `restoredAt` (`CaptureStage+SystemAudioLoss.swift:12-14`).
- A `.notDetermined` mic counts as included (`CaptureSession.swift:187`).

**F7. `config set` accepts any key, and the CLI cannot be pointed at a scratch config (medium, fix now).** Observed: `auricle config set bogus.key x` exits 0 and writes `[bogus] key = "x"`. `Config.defaultFileURL` uses `homeDirectoryForCurrentUser` (`Sources/Core/Config.swift:97`), which ignores `HOME`. No flag or environment variable overrides the path. `ConfigWriter.set` also blames "this edit" when the file was already invalid, which can dead-end onboarding at Done (`Sources/Core/ConfigWriter.swift:80-84`).

**F8. Smaller items (defer, batch).**
- `DoneStepView` logs `String(describing: error)` as `.publicSafe`, which can carry the home path (`App/Auricle/Onboarding/DoneStepView.swift:49`).
- The trigger swallows `start` and `stop` errors without a log line, although the 5.6 I/O matrix says "caught and logged" (`DebugCaptureTrigger.swift:49,53`). A second press during an in-flight start is dropped.
- `CaptureStage`'s default `makeSession` builds a second `PermissionChecker` (`CaptureStage.swift:162`, `LiveCaptureSession.swift:57`).
- A failed start leaves a 44-byte `audio.wav` that `audio_cache_path` points to (`CaptureSession.swift:200-206`).
- Clicking a capture-failed notification does nothing (`NotificationClickHandler.swift:51-53`).
- The configured self link can appear twice in attendees (`SummaryArtifactMapper.swift:149-153`). No production code passes `configuredSelfWikilink` to `AttributionViewModel` (`Sources/Attribute/AttributionViewModel.swift:56`).
- `AuricleApp.swift:16-18` cites `NSUserNotificationsUsageDescription`, which Story 5.1 removed.

### Process lessons

- **Keep the epic's live gate as an open item until it runs (P1).** When a story scopes a live check out as "post-merge practice", the retro or the story adds a tracked action item. Story `done` must not read as the gate being passed.
- **Put the story id in rework commit subjects, and update that story's spec (P2).**
- **Pick up open retro items at the start of the next epic (P3).** Five Epic 4 items are still open.
- **Repair `sprint-status.yaml` before every retro (S6).** Use `sprint_plan.py generate --set` without `--fresh`. `--fresh` resets every story not named in a `--set` to `backlog`, and the fix-flow reference does not warn about that.

## Acceptance verdict

**Rejected** (maintainer decision, matching the machine verdict). Criteria: declared, per story in `epics.md`.

- All 10 stories are `done` by their specs. `make check` passes with 1660 tests.
- The epic's declared end-to-end criterion has no evidence. That criterion is the Story 5.6 dogfood run: launch, onboard, Cmd-Shift-R over a real meeting, find `audio.wav`, finish the note from the terminal. No real meeting has been recorded (S1).
- F1 breaks the path that run uses, and F2 hides data loss on it.

**Exit to accepted:** fix F1, F2 and F4 (action item 1). Then run one real meeting from capture through `awaiting_attribution`, with its `stage_events` metadata recorded in the 5.6 spec (action item 2).
