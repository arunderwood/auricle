## Intent

**Problem:** Nothing edits `~/.auricle/config.toml` in place (FR59). `Config` has no `self.wikilink` key, `auricle config set` is a stub, and Story 5.7/5.9's onboarding writes (vault path, `self.wikilink`) have no target.

**Approach:** Add `Core/ConfigWriter.set(_:to:)`, a single-key TOML editor that edits the raw file text (not a parse-and-reserialize round trip) so it never disturbs comments or unrelated keys, and writes through `AtomicWriter`. Extend `Config`/`RawConfig` with `self.wikilink` → `selfWikilink: String?`. Wire `auricle config set <key> <value>` to call it.

## Boundaries & Constraints

**Always:**
- `ConfigWriter.set(_ key: String, to value: String, fileURL: URL? = nil, homeDirectory: URL = FileManager.default.homeDirectoryForCurrentUser) throws` — `fileURL`/`homeDirectory` mirror `Config.load`'s own test-seam parameters (`Config.defaultFileURL(homeDirectory:)` is the resolution default), so tests never touch the real `~/.auricle`.
- `key` is dotted (`"self.wikilink"`) or bare (`"vault_path"`) — the same two shapes `Config`'s own schema already uses. Support both an existing fully-dotted line (`table.key = ...`) and an existing `[table]` section form as the pre-existing representation to edit in place; when creating a new nested key, always emit the `[table]` section form.
- Changes only the target key's value. Every other key, table, comment, and line of the file is byte-for-byte unchanged, including a trailing inline comment (`# ...`) on the edited line itself, which survives after the new value.
- Creates `~/.auricle/` and `config.toml` when either is absent, writing a file containing only the new key.
- The final write goes through `Core/AtomicWriter.write(_:to:)` — never a direct `Data.write`/`FileManager` write (the existing `atomic_writer_bypass` swiftlint rule already covers `Sources/Core/*.swift`).
- `Config.parse` gains a `self` table: `selfWikilink: String?`, empty-string-means-unset like every other optional string key (`nonEmpty(_:)`, already in `Config.swift`).
- `ConfigVerb.Set.run()` calls `ConfigWriter.set(arguments.key, to: arguments.value)`, replacing its `notYetImplemented` stub, and reports a typed failure the same way `ImportVerb` does (`writeStderr` + non-zero `ExitCode`, not a crash).

**Never:**
- Never parse the whole document into a `TOMLTable` and reserialize it to satisfy "keeps every comment" — verified in `TOMLKit`'s vendored `toml.hpp` (`consume_comment()`, called from the table/array-of-tables parse loops) that the parser discards comment text as it consumes it; nothing attaches a comment to a node, so `TOMLTable(string:).convert(to: .toml)` reproduces values only, never the original comments. Editing must operate on the raw file text.
- Never accept or write a secret through this path (review pass 3): `set` rejects any key matching a credential-shaped pattern (`api_key`, `token`, `secret`, `password`, case-insensitive) with `WriterError.secretRejected`, except the one documented exception `google_calendar.client_secret` (`Config`'s own doc comment: Google issues Desktop-type clients a secret it documents as non-confidential). The Anthropic API key and Google refresh token stay in `KeychainAPIKey`/Keychain (NFR-S1) and are never part of `Config`'s TOML schema.
- Never touch `ConfigVerb.Get` — it stays `notYetImplemented`; this story only wires `Set`.
- `key` paths deeper than one dot (e.g. three-level nesting) are out of scope — no key in `Config`'s current schema needs it.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Existing top-level key | File has `vault_path = "/old"` plus unrelated comments/keys | Only that line's value changes to the new literal; every other line is untouched | No error expected |
| Existing nested key, `[table]` form | File has `[self]\nwikilink = "[[Old]]"` with a comment above it | Only `wikilink`'s value changes; the section header, comment, and any sibling keys in `[self]` are untouched | No error expected |
| Existing nested key, fully-dotted form | File has `self.wikilink = "[[Old]]"` at top level (no `[self]` header) | That line's value changes in place; no duplicate `[self]` section is created | No error expected |
| Key absent, table absent | File has no `[self]` section at all | A new `[self]\nwikilink = "..."` section is appended at end of file | No error expected |
| Key absent, table exists | File has `[self]` with unrelated keys, no `wikilink` | `wikilink = "..."` is appended inside the existing `[self]` section, before the next table header (or EOF) | No error expected |
| File absent | `~/.auricle/config.toml` doesn't exist (and `~/.auricle/` may not either) | Both are created; the file contains only the new key | No error expected |
| Trailing inline comment on the edited line | `wikilink = "[[Old]]" # picked at onboarding` | New value replaces `"[[Old]]"`; ` # picked at onboarding` is preserved unchanged after it | No error expected |
| Value needs TOML escaping | Value contains a `"` and a `\` | Written as a valid, correctly-escaped TOML basic string; `Config.parse` reads back the original unescaped value | No error expected |
| `self.wikilink` round trip | `ConfigWriter.set("self.wikilink", to: "[[Jordan]]")`, then `Config.parse` on the result | `config.selfWikilink == "[[Jordan]]"` | No error expected |

**Acceptance Criteria:**
- Given a config file with unrelated keys and comments, when `ConfigWriter.set` changes one key, then every other line in the file is unchanged and the target key's new value round-trips through `Config.parse`.
- Given no `~/.auricle/config.toml`, when `ConfigWriter.set` is called, then the directory and file are created and contain only the new key.
- Given `auricle config set self.wikilink "[[Jordan]]"`, when the CLI runs, then `ConfigWriter.set` is invoked (not `notYetImplemented`) and a subsequent `Config.load` reports `selfWikilink == "[[Jordan]]"`.
- Given `ConfigWriter.set` fails (e.g. an unwritable `~/.auricle/`), when the CLI verb runs, then it exits non-zero with a message on stderr, not a crash.
- Given `key` is empty, is exactly `"."`, or starts or ends with `.` (e.g. `"self."`, `".wikilink"`), when `ConfigWriter.set` is called, then it throws `WriterError.invalidKey` before reading or writing any file, and no line is inserted or altered. (review iteration 1)
- Given an edit that would leave the file unparseable (an existing inline table, a scalar/table name collision, a quoted key or header, mismatched CRLF/LF, or any other shape `set` doesn't specifically recognize), when `ConfigWriter.set` is called, then it throws `WriterError.wouldProduceInvalidConfig` and the file on disk is unchanged. (review pass 3)
- Given `key` matches a credential-shaped pattern and isn't `google_calendar.client_secret`, when `ConfigWriter.set` is called, then it throws `WriterError.secretRejected` before writing. (review pass 3)
- Given `key` is `diarization_review.enabled` or `attribution.snippet_duration_seconds` and `value` parses as the declared type, when `ConfigWriter.set` is called, then the written literal is unquoted (`true`/`false`/an integer), and `Config.parse` reads it back as that type. (review pass 3)

## Spec Change Log

### 2026-09-22 — Review pass 1 (bad_spec)

**Triggering findings:** Blind Hunter and Edge Case Hunter (two independent findings each, same root cause) found that `ConfigWriter.set` never validates `key`'s shape: a trailing dot (e.g. `"self."`) yields an empty `leaf`, so the code silently inserts a keyless `" = value"` line into the user's hand-edited config file with no error; a leading dot (e.g. `".wikilink"`) yields an empty `table`, so the code silently falls into the bare-key branch and writes a root-level `wikilink` key instead of erroring. Separately, Blind Hunter found that an existing table already defined in inline form (`self = { wikilink = "x" }`) isn't recognized by the `[table]`-header search, so `set` appends a second, block-form `self` section rather than editing the inline one in place — a case this spec's Boundaries never named as supported or excluded.

**What was amended:** Design Notes gained a mandatory key-validation step, run before any file I/O, rejecting an empty key or one with a leading/trailing dot via a new `WriterError.invalidKey` case (Code Map and Tasks & Acceptance updated to match: a new AC bullet, a new test-coverage bullet). Design Notes also gained an explicit "out of scope" paragraph stating that only the two representations already named in Boundaries (fully-dotted line, `[table]` section) are recognized — an inline-table definition of the same table is not detected, and `set` will append a redundant block-form section alongside it. Neither change touches `<intent-contract>`: the fix for the first finding is a Design Notes procedural step (validate before acting), and the fix for the second is a Design Notes scope clarification, not a change to Boundaries' own "Always"/"Never" rules.

**Known-bad state avoided:** a user's hand-maintained `~/.auricle/config.toml` — the exact file FR59 promises is safe to edit by hand — could have been silently corrupted with a malformed line (trailing dot) or had a value land under the wrong key (leading dot) with no error surfaced at all. The inline-table gap is now a documented, deliberate limitation instead of a silent one.

**KEEP instructions (must survive re-derivation):** everything about the original approach was independently verified correct except the two gaps above: raw-text editing instead of a `TOMLTable` parse/reserialize round trip (confirmed necessary — `toml++` discards comments while parsing); `TOMLTable(["v": value]).convert(to: .toml, options: [])` for value-literal formatting (confirmed correct, including that `options: []` is required to avoid `.allowLiteralStrings` rendering a safe value as a single-quoted literal); the root-region/`[table]`-section search-and-replace algorithm, including trailing-comment preservation and blank-line-aware insertion; the `Config`/`RawConfig`/`RawSelfTable` additions; the `ConfigVerb.Set.run()` wiring shape (`do`/`catch` → `writeStderr` + `ExitCode(1)`, matching `ImportVerb`). Re-derive by keeping all of that and adding only the key-shape validation and the inline-table scope note.

### 2026-09-22 — Review pass 3 (external, post-ship)

**Triggering findings:** a peer Claude session, at the maintainer's request, built PR #114's head and ran 17 constructed probe edits against `ConfigWriter.set`, reproducing 9 that made the resulting file unparseable by `Config.parse` (an inline-table `self`, a root-level `self.other` dotted sibling followed by an appended `[self]`, a pre-existing quoted key, a spaced dotted key `self . wikilink`, a quoted header `["self"]`, mismatched CRLF/LF, a multi-line array, a multi-line string, and a `Bool`-typed key written as a string) plus real-name PII in `Config.swift`'s own doc comment and this spec's own body (missed by pass 2's fix, which only touched the two test files), a missing denylist for credential-shaped keys, and a layout nit (no blank line before a header a new root key lands next to). Independently verified in this session by copying the peer's probe test and running it directly: 9/17 cases confirmed `PARSE=FAIL`.

**What was amended:** Boundaries' secret-rejection rule now names the actual enforcement mechanism (a denylist + one documented exception) instead of "no parameter for one." Design Notes' inline-table scope note is corrected to say unrecognized TOML shapes are now safely rejected, not silently corrupted, and gained four new subsections: validate-before-write (`Config.parse` re-check before every `AtomicWriter.write`, the single guard that closes all 9 corruption modes at once), CRLF preservation, schema-aware value typing (`Bool`/`Int` literals for the two non-string schema fields), and the blank-line-before-header insertion fix. None of this touches `<intent-contract>`'s Intent/I-O-matrix; the secret-rejection wording change is the one edit inside Boundaries, correcting a mechanism description rather than the invariant itself (which was already stated and remains unchanged).

**Known-bad state avoided:** any of the 9 reproduced shapes — several of them realistic (a hand-added `self.other = "x"` line, a config edited on Windows or through a CRLF-normalizing tool, a future caller flipping `diarization_review.enabled`) — would have made `Config.load` reject the *entire* file on the next launch or `config get`, not just the edited key. The maintainer's own real name was shipped in committed source in two places pass 2's fix missed (a doc comment, and this spec's own historical text).

**KEEP instructions (must survive any future re-derivation):** the raw-text editing approach, the root-region/`[table]`-section search-and-replace algorithm, the key-shape and bare-key-character validation, the header comment/whitespace tolerance, and the bracket-aware bare-token scanner from passes 1-2 are all still correct and unchanged. Pass 3 adds a validation layer on top (re-parse before write) rather than replacing any of that logic — re-derive by keeping everything from passes 1-2 and adding: the `Config.parse`-based validate-before-write guard, `WriterError.secretRejected`/`.wouldProduceInvalidConfig`, CRLF round-tripping in `apply`, schema-aware literal formatting, and the header-insertion blank line.

## Design Notes

**Why raw-text editing instead of `TOMLTable` parse/reserialize:** `TOMLKit`'s backend (`toml++`) drops comment tokens as it parses (`consume_comment()` in the vendored `toml.hpp`) — nothing in its node model stores them. Round-tripping the whole file through `TOMLTable(string:)` → mutate → `.convert(to: .toml)` would silently delete every comment, which the AC explicitly forbids. `TOMLKit` is still used, but only to format the one new value correctly (quoting/escaping), not to reserialize the document.

**Validate `key` before touching any file** (added review iteration 1 — see Spec Change Log): split on the last `.`, as below, to get `table` (may be empty) and `leaf`. Throw `WriterError.invalidKey(key: key)` first, before any read or write, when `leaf` is empty (covers `key` being empty, exactly `"."`, or ending in `.`) or when `table` is non-empty but starts with `.` or is itself empty-after-the-dot in a way that isn't the ordinary "no dot at all" case (covers `key` starting with `.`, e.g. `".wikilink"`). Concretely: reject whenever `key` is empty, or `key.hasPrefix(".")`, or `key.hasSuffix(".")`. Without this, a leading dot silently drops into the bare-key branch (writing `wikilink` at the root instead of erroring) and a trailing dot writes a keyless `" = value"` line — both silent corruptions of a file `~/.auricle/config.toml` FR59 promises is safe to hand-edit.

**Explicitly out of scope (review iteration 1):** recognizing an inline-table assignment (`self = { wikilink = "x" }`) as an existing occurrence of table `self`. `set` only ever recognizes the two forms named in Boundaries — a fully-dotted line, or a `[table]` section header. Nothing in this codebase (the CLI, or the onboarding writers Stories 5.7/5.9 will add) ever produces inline-table config output, so this only matters for a config file someone hand-wrote using inline-table style — narrow enough that rewriting an inline table's contents in place (a meaningfully bigger feature than a single-key text edit) isn't worth building for this story. **(Corrected, review pass 3):** this used to say the unrecognized inline table "stands alongside" a freshly appended `[table]` section, i.e. that `set` silently wrote a second, conflicting definition of the same name. It did, until pass 3's validate-before-write guard below closed that: `set` still doesn't *edit* an inline table in place, but it no longer *corrupts* one either — the attempt now throws `WriterError.wouldProduceInvalidConfig` and the file is untouched. The same applies to every other TOML shape `set` doesn't specifically recognize (a quoted key or header, a dotted key with embedded spaces, a pre-existing scalar/table name collision, mismatched CRLF/LF within one edit): unrecognized now means "safely rejected," not "silently corrupted."

**Validate before writing (review pass 3):** after computing the candidate `updatedText`, `set` calls `Config.parse(updatedText, homeDirectory:)` — the same parser `Config.load` itself uses — before ever calling `AtomicWriter.write`. If parsing fails for any reason (invalid TOML syntax, a value of the wrong type for a field `Config` declares), `set` throws `WriterError.wouldProduceInvalidConfig(ConfigError)` and the file on disk is untouched. This is a single, general guard: it doesn't make `set` understand any more TOML syntax than before, but it guarantees `set` never *writes* a file `Config.load` can't read back, turning every one of the corruption modes above (and any not yet found) into a clean, typed error instead.

**CRLF preservation (review pass 3):** the line-based logic below only understands `\n`. `apply` now normalizes `\r\n` → `\n` on the way in when the existing text contains any `\r\n`, runs the same logic unchanged, then converts `\n` → `\r\n` back on the way out — so a Windows-authored or `core.autocrlf`-mangled config keeps its own line ending instead of gaining a mismatched all-`\n` section that the validate-before-write guard would then have to reject.

**Schema-aware value typing (review pass 3):** `set` always took `value: String` and always wrote it as a quoted TOML string — correct for `self.wikilink` (this story's own key) but wrong for `Config`'s two non-string fields, `diarization_review.enabled` (`Bool`) and `attribution.snippet_duration_seconds` (`Int`): writing `enabled = "true"` made `Config.parse` throw a type mismatch on every subsequent load, not just for the edited key. `formattedLiteral` now looks up the key's declared type (`bool`/`int`/`string`, `string` for every other key including ones `Config` doesn't recognize) and, when the given string parses as that type, renders an unquoted `true`/`false` or integer literal instead of a quoted string. A value that doesn't parse as its declared type still falls through to the string path, and the validate-before-write guard above catches the resulting mismatch rather than silently writing it.

**Locating and replacing a line, in order:**
1. Split `key` on `.`: `table` = everything but the last component (may be empty), `leaf` = last component.
2. If `table` is non-empty, first look for an existing fully-dotted line `^\s*table\.leaf\s*=` anywhere before the first top-level `[...]` header (the dotted form is only meaningful at the root). If found, replace there.
3. Else if `table` is non-empty, find a `^\[table\]` header line; if present, search within its section (up to the next `^\[` or EOF) for `^\s*leaf\s*=`. Replace if found; otherwise insert `leaf = literal` just before the section ends.
4. Else if `table` is non-empty and no `[table]` section exists, append `\n[table]\nleaf = literal\n` at EOF.
5. Else (`table` empty): search the root region (before the first `^\[` header) for `^\s*leaf\s*=`; replace if found, else insert the new line at the end of that region.
6. **Replacing a found line's value:** everything up to and including `=` and its following whitespace is kept; the existing value token is skipped (a `"..."` or `'...'` span honoring `\"` escapes in the former, or a bare token up to whitespace/`#`/EOL otherwise) and replaced with the new literal; anything after the old value (whitespace + optional `# comment`) is preserved verbatim.
7. **Formatting the literal:** for `diarization_review.enabled`/`attribution.snippet_duration_seconds`, an unquoted `true`/`false`/integer literal when the given value parses as one (review pass 3); otherwise `TOMLTable(["v": value]).convert(to: .toml, options: [])`, then take the substring after `"v = "` (trimming the trailing newline) — reuses `TOMLKit`'s own escaping instead of hand-rolling it.
8. **A brand-new root-level key inserted directly before an existing table header** (step 5's insertion case) gets a blank line inserted after it, ahead of that header, so the new key doesn't visually run into the section below it (review pass 3).
